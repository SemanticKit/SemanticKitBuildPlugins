# Build Plugins

The value is to move repeated manual build and evaluation work into SwiftPM build plugins so the workflow is reproducible, deterministic, and invoked through `swift build`.

The plugin is the captured workflow. It should remove discretion from future runs:

- same inputs from SwiftPM target APIs
- same commands generated by plugin code
- same declared artifacts
- same stdout/stderr diagnostics
- same failure behavior
- no ad hoc shell commands
- no manual OPA invocations during normal use
- no invented per-session process

The doc should explain that purpose first. Then it should document the plugin contracts as automation boundaries, not as shell recipes or stale architecture inventory.

## Plugins

| Plugin | Applied to | Inputs | Command | Declared output |
| --- | --- | --- | --- | --- |
| `RegoPolicyManifest` | a policy target | each `.rego` source file of the target | `RegoPolicyManifestTool --rego <file> --root <root> --output <out>` | `<root with dots>.bundle.tar.gz`: the policy and a `.manifest` whose only root is `<root>` |
| `RegoPolicyCompile` | a policy target, after `RegoPolicyManifest` | each `*.bundle.tar.gz` (or each `.rego` file when the manifest plugin is not applied) | `opa build --target plan --bundle <source bundle>` | `<root with dots>.plan.tar.gz` |
| `RegoPolicyPlanBundle` | a policy target, after `RegoPolicyManifest` | all `*.bundle.tar.gz` of the target (or its `.rego` files) | `opa build --target plan --bundle ...` | `<target>.tar.gz` |
| `RegoPolicyEvaluate` | any Swift target | the `.rego` files of the target and of every target it depends on | `RegoPolicyEvaluateTool plan --opa <opa> --plans <dir> --record <file> --policy ...`, once per target | `RegoPolicyPlans.swift`, a comment line |
| | | the `.swift` files of the target and of every target it depends on | `RegoPolicyEvaluateTool vocabulary --record <file> --source ...`, once per target | `RegoPolicyVocabulary.swift`, a comment line holding the vocabulary as JSON |
| | | each `.swift` file of the target, the plans and the vocabulary | `RegoPolicyEvaluateTool evaluate --plans <dir> --record <file> --vocabulary <file> --source <file>`, once per Swift file | `RegoPolicyFindings.<path in target>.swift`, a comment line |

`<root>` is the policy's path under its target directory without `.rego`: `Sources/AppleHumanInterfaceGuidelines/apple/hig/color/hardcoded_color.rego` has the root `apple/hig/color/hardcoded_color` and must declare `package apple.hig.color.hardcoded_color`. Unique roots keep the per-policy files apart in the target's resource bundle and let `opa build` merge the bundles of a target.

The outputs of the first three plugins are resources of the policy target, for code that links a policy library and evaluates its policies at run time with SwiftOPA; nothing in this repository does that yet. `RegoPolicyEvaluate` does not read them: SwiftPM shows a plugin none of the files that other plugins generate for other targets, so its `plan` command plans the policies it needs itself, into its plugin work directory, and unpacks each plan bundle there for SwiftOPA.

Each command of `RegoPolicyEvaluate` declares only a Swift file holding a comment, so it adds no resources to the target it checks, and the tool rewrites that file only when its line changes. SwiftPM runs the `plan` command again only when a `.rego` file changes, the `vocabulary` command when a Swift file of the target or of its dependencies changes (its record changes only when the vocabulary does), and the `evaluate` command of a Swift file only when that file, the plans or the vocabulary change, so editing one file evaluates that file alone.

`opa` is the OPA CLI. The plugins use the `opa` tool SwiftPM provides, then the first `opa` on `PATH`, then `~/.local/bin/opa`, and stop the build with `opa not found` when there is none.

## Policy contract

A policy file declares one package, a `default decision`, and a `decision` rule annotated as the plan entrypoint:

```rego
package apple.hig.presentation.alert_ok_button

default decision := {"deny": [], "warn": [], "note": []}

# METADATA
# entrypoint: true
decision := {"deny": [], "warn": warnings, "note": []}
```

Each entry of `deny`, `warn` and `note` has `rule_id`, `message`, `line`, `column` and `severity`.

`input` is one Swift file. `RegoPolicyEvaluate` parses each Swift file with SwiftParser, folds its operator sequences with the standard operators (SwiftOperators), and walks it once with a `SyntaxVisitor`. `input` holds one list for each kind of node policies look for, named after the node type, and each node in a list carries its swift-syntax properties by name:

```rego
some call in input.functionCallExprs
call.calledExpression.declReferenceExpr.baseName == "Button"
some argument in call.arguments
some segment in argument.expression.stringLiteralExpr.segments
count(segment.stringSegment.content) > 32
```

| List | Node | Properties |
| --- | --- | --- |
| `functionCallExprs` | `FunctionCallExprSyntax` | `calledExpression`, `arguments` (each `label`, `expression`), `trailingClosure`, `additionalTrailingClosures` |
| `memberAccessExprs` | `MemberAccessExprSyntax` | `base`, `declName` |
| `declReferenceExprs` | `DeclReferenceExprSyntax` | `baseName`, `argumentNames` |
| `stringLiteralExprs` | `StringLiteralExprSyntax` | `segments`, each `{"stringSegment": {"content"}}` or `{"expressionSegment": {"expressions"}}` |
| `infixOperatorExprs` | `InfixOperatorExprSyntax` | `leftOperand`, `operator`, `rightOperand` |
| `dictionaryExprs` | `DictionaryExprSyntax` | `elements`, each `key`, `value` |
| `genericSpecializationExprs` | `GenericSpecializationExprSyntax` | `expression`, `genericArgumentClause` |
| `macroExpansionExprs` | `MacroExpansionExprSyntax` | `macroName`, `arguments`, `trailingClosure` |
| `returnStmts` | `ReturnStmtSyntax` | `expression` |
| `variableDecls` | `VariableDeclSyntax` | `attributes`, `modifiers` (each `name`, `detail`), `bindingSpecifier`, `bindings` (each `pattern`, `typeAnnotation`, `initializer`, `accessorBlock`), `documentation` |
| `functionDecls` | `FunctionDeclSyntax` | `attributes`, `modifiers`, `name`, `genericParameterClause`, `signature` (`parameterClause.parameters`, each `firstName`, `secondName`, `type`; `returnClause.type`), `body`, `documentation` |
| `initializerDecls` | `InitializerDeclSyntax` | `attributes`, `modifiers`, `signature`, `body`, `documentation` |
| `enumCaseDecls` | `EnumCaseDeclSyntax` | `modifiers`, `elements` (each `name`, `parameterClause`, `rawValue`) |
| `structDecls`, `classDecls`, `enumDecls`, `actorDecls`, `protocolDecls` | the type declarations | `attributes`, `modifiers`, `name`, `inheritanceClause.inheritedTypes`, `memberBlock.members` (each `decl`), `documentation` |
| `extensionDecls` | `ExtensionDeclSyntax` | the same, with `extendedType` in place of `name` |
| `identifierTypes`, `memberTypes`, `dictionaryTypes` | `IdentifierTypeSyntax`, `MemberTypeSyntax`, `DictionaryTypeSyntax` | `name` (`baseType` on a member type), `genericArgumentClause`; `key`, `value` |

Every node also has `range`, `{"start": {"line", "column"}, "end": {"line", "column"}}`, 1-based and without trivia. A token is its text. A child that can be one of several kinds of node is an object with one key, the name of its case in swift-syntax's own enum for that kind: an expression is `{"functionCallExpr": {...}}`, `{"memberAccessExpr": {...}}`, `{"stringLiteralExpr": {...}}` (`ExprSyntaxEnum`), a type `{"identifierType": {...}}` (`TypeSyntaxEnum`), a declaration in a member block `{"variableDecl": {...}}` (`DeclSyntaxEnum`), a pattern `{"identifierPattern": {"identifier"}}` (`PatternSyntaxEnum`), and a statement in a body `{"item": {"decl" | "stmt" | "expr": ...}}`. A property that is `nil` or an empty list is left out, so a policy tests for it with `not node.initializer` or `object.get`. `documentation` is the text of the `///` and `/** */` comments before a declaration, one comment per line.

Each node in a list also has `context`: the declarations around it, outermost first, each as in a member block (`{"structDecl": {...}}`) without its `memberBlock`, `body` or the values of its bindings, so a policy can tell whether a call sits in a boundary coder. A list with no nodes is left out. Policies never read nodes by position or by type name: they read the named properties.

`input.vocabulary` holds the terms the ontologies in scope declare: `ontologies`, the types marked `@Ontology` or conforming to `Ontology` in the target and in every target it depends on (`Fauna`); `terms`, the names their `Class("Animal")`, `Property("habitat")`, `Individual(…)`, `Datatype(…)`, `ObjectProperty(…)`, `DatatypeProperty(…)` and `AnnotationProperty(…)` declarations give, and the types declared inside an ontology or an extension of one; `prefixes`, the prefixes their `Prefix("foaf", …)` declarations bind. The `vocabulary` command reads them with a `SyntaxVisitor` (`OntologyVocabularyVisitor`). No policy types a term name. The declarations are read from the Swift source files of the target and of the targets it depends on; SwiftPM does not show a plugin the files other plugins generate, so Swift a translator plugin writes at build time is not in scope.

`RegoPolicyEvaluateTool input [--vocabulary <record>] --source <file.swift>` prints the `input` a file gives policies as JSON. A Rego test fixture is that output for the Swift its comment names, `# Parser output for `<swift>` at <line>:<column>.`, or the vocabulary of the ontologies its comment names, `# Vocabulary of `<swift>`.`, and a Swift test checks that every fixture still matches.

The code in `#if` blocks is part of the input whether or not it is compiled.

## Diagnostics

Each finding prints as

```text
<file>:<line>:<column>: warning: <message> [<rule_id>]
```

with `error` for `deny` entries, `warning` for `warn` entries and `note` for `note` entries. A `deny` entry fails the build.

## Attaching the plugins

A policy target holds `.rego` files and applies the three policy plugins:

```swift
.target(
    name: "AppleHumanInterfaceGuidelines",
    plugins: [
        .plugin(name: "RegoPolicyManifest"),
        .plugin(name: "RegoPolicyCompile"),
        .plugin(name: "RegoPolicyPlanBundle"),
    ]
)
```

A package that wants its Swift checked depends on the policy libraries and applies `RegoPolicyEvaluate`:

```swift
dependencies: [
    .package(url: "https://github.com/SemanticKit/SemanticKitBuildPlugins", branch: "main"),
],
targets: [
    .target(
        name: "App",
        dependencies: [
            .product(name: "AppleHumanInterfaceGuidelines", package: "SemanticKitBuildPlugins"),
            .product(name: "SemanticKitDesignGuidelines", package: "SemanticKitBuildPlugins"),
        ],
        plugins: [
            .plugin(name: "RegoPolicyEvaluate", package: "SemanticKitBuildPlugins"),
        ]
    ),
]
```

`Tests/PolicyConsumer` is such a package, with three targets. `PolicyOntologies` holds the ontology declarations in scope, and the other two depend on it. `swift build --target PolicyConsumer` reports every `warn` and `note` rule of both libraries from `PolicyTriggers.swift` and passes: `Intended.swift` holds the shapes the SemanticKit invariants allow. `swift build --target PolicyProbes` fails: `Banned.swift` holds one shape per line that a `deny` rule of `SemanticKitDesignGuidelines` names, and the build prints each with its rule. The shapes sit in `#if false` blocks, which the policies read and the compiler skips. `ConsumerBuildTests` runs both builds (see [Tests](#tests)).

## SemanticKit invariants

`SemanticKitDesignGuidelines` holds the SemanticKit invariants as `deny` rules: each one fails the build of a target that depends on the library and applies `RegoPolicyEvaluate`, with the rule's id in the diagnostic. They hold the identity rule: inside the Swift runtime the type is the term's identity, and an IRI is read only at the boundary. A boundary target (a translator into SHACL or SPARQL, the HTTP layer) need not depend on the library, and then the rules do not run there. A format's encoder and decoder may also live in a target the rules run on: inside one, `no_interpolated_identity` lets the format build IRIs from text (see the table).

| `no_static_term_enum` | terms kept as statics on a type, or as enum cases. On an enum, any stored static (`enum Fauna { static let animal = … }`), and a static typed `IRI` or a term kind. An enum named or documented as a vocabulary that has cases or statics: `enum Foaf { case knows, person, agent }`, `enum FoafTerm: String { case knows }`, `/// The FOAF vocabulary.` on `enum Friend { case knows }`. The library also holds `no_dictionary_boundary_plumbing`, a `warn` rule.

## Tests

`opa test Sources Tests/Rego` runs the policy tests, and `swift test` runs them too. Each test's `input` is what `RegoPolicyEvaluateTool input` writes for the line of Swift in the comment above it.

`swift test` runs the evaluator's tests in `Tests/RegoPolicyEvaluateToolTests`, with `opa` on `PATH` or in `~/.local/bin`. They parse the Swift in every fixture comment and check that the fixture is the input the evaluator writes for it, so the Rego tests keep testing what policies see at build time. They also plan and evaluate a `deny` policy and check the diagnostic and the exit status, run the `SemanticKitDesignGuidelines` policies over a Swift file with one banned shape per line (each fails with its rule, the tool exits 1) and over the same file with the intended shapes (the tool exits 0), with a vocabulary collected from ontology declarations in scope, run `swift build` of `Tests/PolicyConsumer` (the `PolicyProbes` target fails with every banned shape's rule, the `PolicyConsumer` target passes) and check that its sources are those same shapes, check the vocabulary the ontology declarations give, check that every library policy plans and loads, check the named properties of the input, and check how decisions decode.
